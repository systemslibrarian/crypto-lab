# Crypto Lab audit corpus

Everything an external auditor needs to review every lab in the fleet, from one
fetch instead of 252 clones. Generated by `scripts/build-audit-corpus.js` from
`scripts/corpus-readme.md`; never hand-edited in place — edit the template.

## The three rules this corpus is built on

**1. Cite `commit_sha` + `slug` + field for every finding.** Each record pins the
commit its bytes were read from. A finding without that triple cannot be checked
later, because labs move: 113 of them moved on the day this was written.

**2. `commit_sha` is the commit that was READ, not the branch tip.** When a
checkout is behind its remote, `commits_behind_remote` says by how much and
`remote_head` names the tip. Both are recorded so staleness is visible instead of
hidden. If `commits_behind_remote` is greater than 0, the lab's live site may be
ahead of this record — check `remote_head` before reporting a lab as wrong.

Every file a record names is a file that commit CONTAINS, so an anchor can be
opened at `commit_sha`. That needed enforcing rather than assuming: `git status`
is silent about **gitignored** paths, so a checkout holding only build and run
output looks clean, and four labs were published naming files no clone has —
`mutation-report.json` and `mutation-results.json` left by local mutation runs in
three labs, and `pkg/`, wasm-pack output, in a fourth, whose RFC 8439 citation was
anchored in a generated `.d.ts`. The generator now lists `HEAD` and reads nothing
outside it, and `byte` counts are the length of the normalised content rather than
the size on disk, which a CRLF checkout inflates.

**3. `MISSING` means the generator did not find it, NOT that the lab lacks it.**
Every field found records the file it came from in `sources`. A field in `missing`
is an invitation to look, not a defect to report. Treating `missing` as a finding
is the single most likely way to misuse this corpus.

## Files

| File | What it is |
|---|---|
| `index.json` | counts, per-category and per-level tallies, and every lab with missing fields |
| `index.md` | **navigation only.** It says so on its first line, and names the assembly command when the prose is sharded |
| `labs.jsonl` | one JSON record per lab, one per line — the machine-readable corpus, and the ONLY place the full README text lives |
| `labs-full.md` | the prose form, written **only when it really holds the content**. When the prose would exceed 4 MB it is absent and the category shards carry it |
| `labs-full-<category>.md` | category shards, present only when one document would exceed 4 MB |

**The prose files carry each README's FIRST SECTION and a link, not the whole
thing.** Embedding every README put each one in the corpus twice and took the
total to 17.6 MB; the full text is in `labs.jsonl`, which is the file a machine
reads. A `claims` assertion records its file, line, matcher and expected value
but NOT the source line itself — that was a fourth copy of something one `sed -n`
away, and the largest field in the corpus.

Start at `index.json`. It tells you the lab count, whether the corpus is
`complete` against the registry, which clones were behind, and exactly which
labs are missing which fields.

## Record schema

| Field | Meaning |
|---|---|
| `slug`, `repo`, `repo_url`, `live_url` | identity; `live_url` is the card's own href |
| `commit_sha` | **the commit these bytes were read from** — cite this |
| `remote_head`, `commits_behind_remote` | the remote tip, and how far behind the read commit is |
| `read_from` | `working tree (clean)`, or `git archive HEAD` when the clone was dirty |
| `generated_at` | ISO timestamp of the run |
| `clone_present` | false means nothing could be read; everything else will be `missing` |
| `name`, `subtitle`, `description`, `why_it_matters` | the four hero text roles of `audits/_MASTER-TEMPLATE.md` §3.1 |
| `accent` | the lab's own `--accent`, as written. `MISSING` means **no declaration was found** — about 49 labs declare none and inherit the fleet default, which is a documented state, not a bug |
| `category`, `level` | from the card's `data-category` and `data-level`, HTML entities decoded |
| `card` | the catalog's own view: title, kicker, copy, chips, dates, review pin and note |
| `algorithms` | `implements`, `attacks`, `comment_only` (each `{term, anchor}`), plus `references`, `standards`, `implementation`. **Derived from the lab's source by `catalog-evidence.js`, never hand-written.** `comment_only` means the algorithm is named in a code comment and never in anything that executes |
| `spec_citations` | FIPS / RFC / SP 800 / NIST IR / ePrint / arXiv / DOI / ISO / IETF draft / conference strings, **exactly as the lab writes them**, with the file and line each was first seen at. Not normalised, deliberately: normalising is how `SP 800-227` and `SP 800-22` become one citation |
| `readme` | the full README text (`readme_truncated` if it exceeded 400 KB) |
| `claims` | the lab's `claims.spec.ts`: every test name, and every assertion's matcher, line, and expected value **as written** |
| `mutations` | every file matching `/mutation/i` — the §4.1c records — parsed when JSON, raw text otherwise |
| `verification` | the `verification/` manifest and its file contents, when the lab has one |
| `limitations` | `page_panels` (honesty panels in the served page) and `readme_sections` (the README's own "What Can Go Wrong" and equivalents), kept apart because a lab can be honest in one and silent in the other |
| `pages_found` | every visitable HTML page discovered, nearest the root first |
| `missing` | fields the generator could not find — see rule 3 |
| `sources` | per field, the repo-relative file it was read from |

### Reading `claims` well

`expected_kind` is the field to sort by, and `audits/_MASTER-TEMPLATE.md` §4.1b
says why: a test whose expected value is an **expression** re-derived the claim
from the page's own output, while a **literal** was typed by the author and will
agree with a bug as happily as with a fix. A lab whose claims are all literals
is not necessarily wrong, but it is the place to look first.

`expected_kind` is one of `literal`, `expression`, `regex`, or `none`
(a matcher such as `toBeVisible` that takes no expected value).

## How an auditor should use this

1. Fetch `index.json`. Note `lab_count`, `complete`, and `clones_behind_remote`.
2. Fetch `labs.jsonl` (or the category shard you care about).
3. For each claim you want to check, read `claims`, `spec_citations` and
   `limitations` together — the assertion, the standard it rests on, and what the
   lab already says it does not prove. A "finding" the lab discloses in its own
   honesty panel is not a finding.
4. Check `algorithms.comment_only` before reporting an uncredited algorithm: the
   catalog deliberately does not credit an implementation to a comment.
5. Report as: `<slug> @ <commit_sha> — <field>: <finding>`.

## What is deliberately not here

- **Built bundles and served bytes.** This corpus describes committed source. A
  lab's live site can be behind its own `main`; `tools/deploy-sync.js` is what
  answers that, and no static file can.
- **Test results.** The corpus records which claims are *asserted*, never whether
  a run passed. A green run is not a claim about the code and is not archived here.
- **Games.** `games/` is deliberately outside the exhibit catalog; see the root
  `CLAUDE.md`.

## One thing in a record is rewritten, and it is marked

Every field is otherwise the lab's own bytes. The exception: **absolute local
paths are normalised at build time**, because `corpus/` is served from `main` and
a lab's committed path becomes a published one.

Lab content carries them more often than you would expect — vitest prints its
project root, Playwright prints absolute stack frames, and a lab that commits a
captured run commits those too. `crypto-lab-vector-gate` is the case: its
`audits/mutation-observations.json` held a lane worktree path 14 times, and the
first build of this corpus published all 14.

| in the record | means |
|---|---|
| `e2e/claims.spec.ts:25:61` | a path inside the checkout this record was read from, kept relative to the repository, because that part is true of every clone |
| `.` | the checkout root itself |
| `<local-path>` | a home-rooted path the generator could not place inside this checkout — another working copy, a browser cache. **Generated text, not the lab's** |

So `<local-path>` is the one token in a record that is this generator speaking.
Nothing is hand-edited: the corpus is generated, and a hand-edit would be undone
by the next run while looking like a fix. The generator **refuses to write**
`labs.jsonl` or `labs-full.md` at all if a local path survives into either, names
the lab and field it came from, and `--check` fails on an already-published
document that carries one.

## Regenerating

```sh
node scripts/build-audit-corpus.js            # writes corpus/
node scripts/build-audit-corpus.js --check    # fails if any carded lab is absent
node scripts/build-audit-corpus.js --lab kem-trap   # one lab, for debugging
```

The generator **only reads** the lab checkouts; it writes nothing outside
`corpus/`. Dirty clones are read from their committed HEAD through
`tools/clone-source.js`, and a clone that changes mid-run aborts the write as a
torn snapshot rather than mixing two states.

`.github/workflows/audit-corpus.yml` regenerates it on a schedule and whenever
the catalog changes, and fails if a lab in the registry is missing from the
corpus.
