Who this is for

Instructors in computer science, security and information science who want students to see a cryptographic mechanism work, and fail, rather than read about it. Each exhibit isolates one idea and runs in the browser; the modules below group a few of them into a sequence that fits one or two class meetings.

If you are learning on your own, the catalog’s learning paths are built for you. Modules are built for a course: each one states its audience, prerequisites and outcomes, and gives discussion questions and public instructor notes.

Modules

This is a menu, not a curriculum. Take one module, take one exhibit from a module, or reorder them to fit your course. Class times are estimates for the core sequence; extensions are optional.

  • Security & symmetric encryption

    Fits the symmetric-encryption unit of an introductory computer-security course, or the modes-of-operation and misuse week of an upper-division applied-cryptography course. Planned across two class meetings of about 75 minutes each (Hidden Bit, OTP Vault and AES Modes, then Padding Oracle and Nonce Collision); with shorter meetings, set the worksheets’ Predict questions before class.

    Audience: Undergraduate computer science and security students, from an introductory security course through upper-division applied cryptography, and motivated newcomers comfortable with XOR and hexadecimal.
    Exhibits: Hidden Bit · OTP Vault · AES Modes · Padding Oracle · Nonce Collision
    Class time: about 115 minutes for the core sequence
    Worksheets: AES Modes · Hidden Bit · Nonce Collision · OTP Vault · Padding Oracle

  • Public-key & signatures

    Fits the public-key unit of an undergraduate computer security, network security, or applied cryptography course, as about 150 minutes of lab time: RSA first (Educational RSA, RSA Forge), then elliptic curves (EC Point Arithmetic, ECDSA Forge), which fits two meetings of about 75 minutes with the Predict and Explain sections set outside class, or three meetings of about 50. The nonce-lattice extension suits a cryptanalysis elective or an advanced assignment for students comfortable with vectors and bases.

    Audience: Upper-division undergraduate CS and security students, and motivated newcomers, meeting public-key encryption and digital signatures with the math worked on small numbers before real key sizes appear.
    Exhibits: Educational RSA · RSA Forge · Point Arithmetic · ECDSA Forge · Nonce Lattice extension
    Class time: about 150 minutes for the core sequence
    Worksheets: Point Arithmetic · ECDSA Forge · Nonce Lattice · Educational RSA · RSA Forge

  • Key exchange & secure channels

    Fits the key-exchange or TLS unit of an undergraduate computer networking, network security, or introductory cryptography course. The extension exhibit suits an upper-level security or formal-methods course that introduces symbolic protocol analysis.

    Audience: Undergraduate computer science, networking, and security students, and motivated newcomers, who can follow modular arithmetic and want to see how two parties agree on a key over an open network and what stops an attacker from sitting in the middle.
    Exhibits: DH MITM · TLS Handshake · Downgrade Wire · Protocol Checker extension
    Class time: about 77 minutes for the core sequence
    Worksheets: DH MITM · Downgrade Wire · Protocol Checker · TLS Handshake

  • Post-quantum transition

    Upper-division undergraduate or graduate courses in computer security, applied cryptography or network security, as a two-meeting unit on the quantum threat to public-key cryptography and the move to ML-KEM and hybrid key exchange.

    Audience: Upper-division undergraduate or graduate security students, including motivated newcomers to quantum algorithms and lattice-based cryptography.
    Exhibits: Shor · Grover · Lattice Gentle · Kyber Vault · Hybrid Wire · Harvest Vault extension
    Class time: about 95 minutes for the core sequence
    Worksheets: in preparation

  • Library privacy, for iSchools

    Fits an undergraduate or graduate LIS course on information ethics, privacy, or library systems and technology, as a one- or two-meeting unit. The shelf-oracle extension suits students who also take a technical or information-security elective.

    Audience: Library and information science students in an iSchool, with no mathematics or cryptography background, who need to reason about who can learn what about a patron from a catalog search, a request log, or a published statistic.
    Exhibits: Patron Shield · Blind Relay · DP Noise · Shelf Oracle extension
    Class time: about 60 minutes for the core sequence
    Worksheets: in preparation

For your syllabus

A line you can paste into a syllabus or an assignment:

Crypto Lab exhibits are teaching demonstrations, not production libraries. Do not use exhibit code to protect real data.

How exhibits are checked

Each exhibit is its own repository and its own site, built and published by its own GitHub Actions workflow. The lab standard asks that a lab’s publish step wait for its unit tests, including known-answer tests from the specification it implements, and for a browser test suite, run through Playwright, that includes an automated accessibility scan (axe-core, WCAG 2.1 A and AA rules) of the built site. It also asks for a “claims” suite that checks what a page says against what the page computes.

Practice varies from lab to lab. Reading the workflow files that publish the labs on 2026-09-22, we found that most run both a unit suite and a browser suite, while some run only one of the two. Most test in Chromium only; a few also test in Firefox and WebKit, the engine behind Safari. Many labs have a claims suite and some do not. A green build therefore means different things for different labs.

What these checks do not establish: that an explanation teaches well, that a lab behaves the same in browsers its tests do not run, how it works with a screen reader or keyboard alone, or that its cryptography is free of mistakes its tests do not cover.

The worksheet drift check

Once a day, a scheduled job opens the live exhibit behind each worksheet and looks for every control the worksheet names. If one is missing, it opens an issue in this repository naming the worksheet, so a missing control is usually reported within a day of the change going live. It cannot stop a lab from publishing the change, and it cannot confirm that the lab still behaves the way the worksheet describes; it only confirms that the named controls are still on the page.

The pages under /teach/ are generated from data files in this repository, and a check in this repository’s CI fails when a generated page no longer matches its sources.

Accessibility

What is tested automatically

  • In labs whose workflows include the browser suite, axe-core checks WCAG 2.1 A and AA rules against the built site before it is published, usually in Chromium only. Some labs add their own contrast and non-text checks.
  • The catalog page was scanned with axe-core by hand on 2026-09-22, before and after the links to these pages were added; axe reported no violations either time. The catalog page has no automated accessibility check in CI.
  • These teaching pages were scanned with axe-core by hand on 2026-09-22 before publication; axe reported no violations. They have no automated accessibility check in CI.

What is not tested automatically

A full keyboard-only walk through an exhibit, use with a screen reader, zoom and reflow, legibility on a classroom projector, motion and timing in animations, and cognitive load. These need a person.

Passing axe is not conformance. Automated rules find some kinds of barriers and cannot judge many others, so nothing on this site claims conformance with WCAG.

Reporting a barrier

Open a teaching material problem report and choose “Accessibility barrier”. Say which page or exhibit, which browser, which assistive technology if any, and what got in the way. If a student cannot use GitHub, an instructor can file the report for them.

What the exhibits contact

Each exhibit is a separate site on systemslibrarian.github.io and makes its own requests. Some labs load web fonts from Google Fonts. The lab standard has a lab write one localStorage key, theme, to keep its single dark theme, and some labs also store settings of their own, such as the last configuration used. Each module page lists what was observed for its exhibits, with the date, once they have been checked.

Blind Oracle is the exception the catalog itself names: its card says it has a live backend. When its page loads it contacts https://blind-oracle-api.onrender.com (a request to /health), and the numbers you encrypt are sent there as ciphertext, with a public evaluation key, for the server to add. Observed 2026-09-22 in Chromium, driven by Playwright; server address read from the lab's .env.production at commit 8dd04f298223.

Hosting

The catalog, these pages and the exhibits are served by GitHub Pages. For what GitHub records about visitors to Pages sites, see GitHub’s own documentation: GitHub Pages data collection.

How to cite

The collection

APA:

Clark, P. A. (2026). Crypto Lab (Version 2026.09.22) [Computer software]. https://crypto-lab.systemslibrarian.dev/

@misc{clark_crypto_lab_2026,
  author       = {Clark, Paul A.},
  title        = {Crypto Lab},
  year         = {2026},
  version      = {2026.09.22},
  howpublished = {\url{https://crypto-lab.systemslibrarian.dev/}},
  note         = {Accessed [date accessed]}
}

Reference managers can also read the CITATION.cff file in the repository, and these pages carry Dublin Core and citation_* metadata.
