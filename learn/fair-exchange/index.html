    E-K-05 · Executable protocol depth

    ASW Protocol E: optimistic signature exchange

    This bounded adaptation follows the expanded 1999 Asokan–Shoup–Waidner report. Bob first sends a verifiable Schnorr signature promise. Alice returns a condition-bound RSA-OAEP escrow of her actual signature; Bob returns a cut-and-choose verifiable escrow of the inverse that completes his promise. The verifier draws its challenge only after receiving the aggregate commitment. Only then does Alice send her signature and Bob send his inverse directly. The normal E1–E6 path contacts the trusted intermediary zero times.

      Run the decisive schedules

      Each button creates fresh participant keys, promises and escrows before executing the named schedule. The browser reuses the same simulated TTP key. The two race buttons contain the same requests in opposite serialized orders.

      Abort wins

      The TTP records ABORT; B-resolve must refuse. Neither escrow becomes a usable peer signature.

      B-resolve wins

      The TTP validates Alice’s escrow, stores Bob’s matching DEPOSIT, and releases Alice’s signature to Bob. A later abort returns the deposit to Alice rather than contradicting the first decision.

      A-resolve wins

      The TTP records NO-ABORT before checking the escrows, then recovers Bob’s promised signature for Alice. Bob can still resolve Alice’s escrow; a later abort must refuse. As the paper specifies, an escrow error does not roll back that record.

      Availability is separate

      There is no synchronized-clock timeout. A party can force a compatible result only when the honest TTP eventually becomes reachable and processes requests atomically.

      What “evidence” means here

      Bob’s promise and Protocol D escrow are verified recoverable evidence: they are bound to this transaction and give the TTP a checked recovery path, but they are not yet Bob’s usable signature. Alice’s alpha is deliberately an ordinary, non-verifiable escrow: Bob receives its ciphertext, but only the TTP can decrypt it and check that it contains Alice’s valid signature. The custody cards separately report signatures that each recipient can independently verify now.

      RSA-OAEP labels bind both escrows to the transaction, Alice’s key and message, and Bob’s promise; Bob’s escrow also binds Alice’s escrow ciphertext, as Protocol E requires. Client-side labels alone would not suffice; the label is checked by actual OAEP decryption.

      Bounded teaching model

      The paper’s example implementation sets 40 interactive cut-and-choose rounds. This page runs 16 so every current session stays inspectable. Conditioned on a uniformly sampled nonzero challenge, a transcript compatible with only one challenge vector is selected with probability 1/65,535. That calculation is not a production security claim and does not transfer the paper’s random-oracle theorem to this adaptation.

      The Schnorr reduction uses the RFC 7919 ffdhe2048 group and SHA-256; escrow uses 3072-bit RSA-OAEP with SHA-256 and exponent 65537. Domain-separated SHA-256 expansion and rejection sampling instantiate Protocol D’s H1, while a separate SHA-256 domain instantiates H2; the verifier samples its challenge only after the aggregate H2 commitment is fixed. These are declared teaching choices. The ordinary and verifiable escrows share one TTP key only under the report’s specific Remark 20 allowance for its suggested implementation. RFC 7919 does not standardize Schnorr or ASW.

      Assumptions that the browser cannot supply

      ASW assumes an honest TTP that is eventually available, processes each request atomically, and preserves its transaction records. Here “atomically” means requests do not interleave; Protocol E deliberately writes NO-ABORT before A-resolve's escrow checks and does not roll it back on a later error. The original model assumes a private client–TTP channel and authenticated server responses, but does not require authenticated client requests. This page simulates one transaction with session-generated request fields in one process; it does not provide an adversarial network/API, authenticated identities, private network channels, crash-safe replicated storage, certificates, production parameter review, or a deployment security proof. The lost-state control shows why durable state is substantive: erase a prior DEPOSIT, then allow a contradictory ABORT, and one party can be left with the only usable peer signature.
